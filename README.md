# xArm6 in MuJoCo: Grid Path Following with a Downward-Facing Tool

A simulation of the UFactory **xArm6** robot arm in **MuJoCo**, built as the foundation of a Deep Reinforcement Learning (DRL) project. The arm moves a suction-style tool across an 8x8 grid on a board, following a path from a start cell to an end cell while keeping the tool pointing straight down.

The long-term goal is a pick-and-place system where RL handles the path-finding. This README documents what has been built so far, how to reproduce it, how the code works, and what comes next.

## 1. Project goal

The end goal is a system that:

1. Detects a wooden piece on a table using computer vision.
2. Picks it up with a vacuum suction tool.
3. Carries it through a maze of obstacles to a destination.
4. Places it at the destination.

The **path-finding** stage is where reinforcement learning is used. The policy should generalize: it should still work when the start position, end position, and obstacle layout change.

The work is simulation-first. Running on the physical xArm6 is a later goal.

## 2. Current status

Done:

- xArm6 model converted from the official `xarm_ros2` repository into a MuJoCo model.
- Scene with a board, a goal marker, a floor, lighting, and position actuators for all six joints.
- Stable simulation (shaking fixed with joint armature, damping and a better integrator).
- A grid on the board with conversion from cell index to table coordinates in meters.
- Inverse kinematics (IK) that places the tool tip at an (x, y, z) target **and** keeps the tool axis pointing straight down.
- Straight-line movement from cell to cell along a path, verified in the viewer.

Not done yet:

- Obstacles / maze in the scene.
- Obstacle-aware path planning (A*) and the RL policy.
- A gripper or suction cup model (the tool is currently defined mathematically).
- Computer vision, grasping, and placing.
- Any work on the real arm.

## 5. Step 1: Build the robot model

UFactory ships the robot as **xacro** templates (templated URDF) written for ROS, and MuJoCo cannot read these directly. `make_xarm6.py` converts them in these stages:

1. **Copy** the `xarm_description` package into `xarm6_mujoco/` so the originals are never modified.
2. **Replace** `$(find xarm_description)` in every xacro file with the real folder path (this substitution normally needs a ROS install).
3. **Run xacro** on the top-level device file with `dof=6` and `robot_type=xarm`. Running `xarm6.urdf.xacro` alone produces an empty robot (0 joints), because that file only defines a macro.
4. **Fix mesh paths** from `package://xarm_description/meshes/...` to relative paths MuJoCo can load.
5. **Insert a `<mujoco>` compiler tag** (`balanceinertia="true"`, `discardvisual="false"`) so MuJoCo keeps the visual meshes and fixes unrealistic inertias.
6. **Load the URDF in MuJoCo** and save it as `xarm6.xml`.

The key line that makes the conversion work:

```python
xacro_file = os.path.join(copy, "urdf", "xarm_device.urdf.xacro")
doc = xacro.process_file(xacro_file, mappings={"dof": "6", "robot_type": "xarm"})
```

Run it:

```bat
python make_xarm6.py
```

Expected output:

```
links in urdf: 10
dae references: 0
joints: 6 bodies: 7
0 joint1
...
5 joint6
```

Notes:

- 10 links vs 7 bodies is normal. MuJoCo merges links connected by fixed joints.
- The xArm6 meshes are `.stl`, which MuJoCo reads directly. `.dae` files are not supported.

## 6. Step 2: The scene file

`scene.xml` assembles the whole simulated world. It includes the generated robot and adds everything else.

| Section | What it does |
|---|---|
| `<default>` | Sets joint `armature="0.1"`, `damping="2"`, `frictionloss="0.1"` for all joints. Placed **before** the include so it applies to the robot. |
| `<include file="xarm6.xml"/>` | Pulls in the generated robot. |
| `<option>` | Gravity, `timestep="0.002"`, `integrator="implicitfast"`. |
| `<visual>` | Brighter headlight so the scene is easier to see. |
| Board geom | 0.5 m x 0.5 m x 2 cm box centered at (0.4, 0), top surface at z = 0.02. |
| Goal body | A red sphere marker (`mocap="true"`, collisions off). Moved from code, not by physics. Not used by `path_move.py` yet. |
| Floor and light | Plane and a lamp above the scene. |
| `<actuator>` | Six position actuators (`act1` to `act6`), one per joint, with `kp`/`kv` gains. |

Position actuators apply force = `kp` x (target angle - current angle) - `kv` x (joint speed). In code, the six target angles are set with `data.ctrl[:6] = q`.

Check the scene in the viewer without any code:

```bat
cd xarm6_mujoco
python -m mujoco.viewer --mjcf scene.xml
```

The **Control** panel on the right has one slider per joint.

### How the grid sits on the board

| | x range (m) | y range (m) |
|---|---|---|
| Board | 0.15 to 0.65 | -0.25 to 0.25 |
| Grid (`X_MIN=0.2`, `Y_MIN=-0.2`, 8 cells of 5 cm) | 0.2 to 0.6 | -0.2 to 0.2 |

The grid sits inside the board with a 5 cm margin. If the board or grid settings change, keep the two consistent.

## 7. Step 3: Move the arm along a grid path

```bat
cd xarm6_mujoco
python path_move.py
```

The script places the arm at the start cell, then visits each cell on the path in order, printing the target, the measured position, and the tool tilt for each:

```
start pose: position error 0.0005 m, tilt 0.1 deg
path: [(0, 0), (1, 1), (2, 2), ...]
cell (0, 0) target (0.225, -0.175) actual [ 0.219 -0.171] tilt 1.2 deg ok
...
```

Change the route by editing `START_CELL` and `END_CELL` near the top of the file. The cell notation is (column `i`, row `j`).

## 8. How the code works

### Settings

| Name | Meaning |
|---|---|
| `X_MIN, Y_MIN` | Board corner of the grid, in meters, in the MuJoCo world frame |
| `CELL`, `N` | Cell size (m) and number of cells per side |
| `CARRY_Z` | Height of the tool tip while moving |
| `START_CELL`, `END_CELL` | Ends of the path |
| `BODY_NAME` | The last link of the arm (`link6`) |
| `TOOL_AXIS` | Direction the suction cup points, in `link6`'s own frame |
| `TOOL_OFFSET` | Distance from the flange to the cup tip, in `link6`'s frame |
| `DOWN` | The world direction the tool should point: (0, 0, -1) |

### Grid helpers

- `cell_to_xy(i, j)` converts a cell index to table coordinates at the cell center.
- `make_path(start, end)` returns the list of cells along a straight line from start to end, using a plain loop. This is the function that will later be replaced by an obstacle-aware planner or the RL policy.

### Tool state

`tool_state(d)` computes, in the world frame:

- the tool tip position (flange position + rotated tool offset), and
- the direction the tool is pointing (rotated tool axis).

`tilt_degrees(axis)` is the angle between that direction and straight down.

### Inverse kinematics (`solve_ik`)

IK answers "which six joint angles put the tool tip at this point, pointing down?" It works by repeated small corrections on a scratch copy of the simulation data:

1. Compute the position error (target minus tip) and the orientation error (`cross(axis, DOWN)`, which is zero when the tool points down).
2. Get the Jacobian from MuJoCo (`mj_jac`): how each joint's motion moves and rotates the tool. Position and rotation rows are stacked into a 6x6 matrix.
3. Compute joint changes with damped least squares: `dq = J^T (J J^T + 1e-4 I)^-1 err`. The damping term keeps steps stable near awkward poses.
4. Apply half the step, clip to the joint limits, and repeat (up to 300 times, stopping at under 1 mm error).
5. Return the joint angles, the final position error, and the final tilt, so the caller can reject bad solutions.

Rotation around the tool axis is left free. A suction cup is rotationally symmetric, so this gives the solver extra freedom.

### Moving between cells (`move_to_xy`)

Solving IK only for the final point would send each joint on its own path, and the tool would swing along an unpredictable curve. Instead:

1. Split the straight line from the current tip position to the goal into 8 waypoints.
2. Solve IK at each waypoint, **starting from the previous solution** so the arm doesn't jump to a different pose.
3. Reject a waypoint if the position error exceeds 1 cm or the tilt exceeds 5 degrees.
4. Write the angles to `data.ctrl[:6]` and run 60 physics steps so the arm follows.

### Start pose

The script solves IK for the start cell and writes the result directly into `data.qpos` and `data.ctrl`, so the arm begins at the start cell instead of swinging there from the home pose.

## 9. Tuning notes

### Shaking at startup

The arm initially vibrated. Cause: stiff position actuators on very light links, which the default integrator could not handle. Fixes that worked (all in `scene.xml`):

- `integrator="implicitfast"`
- joint `armature="0.1"`, `damping="2"`, `frictionloss="0.1"`
- `timestep="0.002"`

### Position lag of about 1 cm

Measured positions land about 1 cm short of the targets because the soft position actuators sag under gravity. Optional fix: add this line right after creating `data` in `path_move.py`:

```python
model.body_gravcomp[:] = 1.0
```

This compensates gravity for every link. Raising `kp` on the first three joints also reduces it.

### Actuator gains

Current values: `kp` 1000 / 1000 / 800 / 500 / 500 / 300 with `kv` at one tenth of `kp`. If the arm sags, raise `kp`. If it jitters, raise `kv` or lower `kp`.

## 10. Known limitations

- **Tool geometry is assumed.** `TOOL_AXIS = (0, 0, 1)` and `TOOL_OFFSET = (0, 0, 0.05)` are assumptions about `link6`. Check in the viewer that the flange faces the board when the printed tilt is near 0. If not, try other axes (`[1,0,0]`, `[0,1,0]`, `[0,0,-1]`). Set the offset to the real cup length once the tool is chosen.
- **No physical tool.** The suction cup does not exist as geometry yet, so it has no collisions and cannot hold anything.
- **Reachability while pointing down.** Some cells (especially close to the base) can be hard to reach with the tool vertical. In one run IK failed at the step toward cell (4, 4), and in the viewer joint 4 sat at the top of its range (6.28). The 1 cm failure threshold is also strict for intermediate waypoints. Options if this happens: move the board farther from the base, raise `CARRY_Z`, restrict the grid to reachable cells, or loosen the waypoint error threshold to about 2 cm.
- **Straight-line paths only.** `make_path` ignores obstacles because none exist yet.
- **Position control only.** The arm follows joint targets, with no force or contact control.
- **The goal marker is unused** by the movement script.

## 11. Troubleshooting

| Problem | Likely cause and fix |
|---|---|
| `links in urdf: 0` | Running `xarm6.urdf.xacro` directly. Use `xarm_device.urdf.xacro` with `dof` and `robot_type` mappings. |
| xacro error about `$(find ...)` | The substitution step did not run. Check the replacement loop in `make_xarm6.py`. |
| Meshes missing or grey | Mesh paths in `xarm6.xml` do not match the folder layout. |
| `dae references` above 0 | MuJoCo cannot read `.dae`. Use the `.stl` version of the mesh. |
| Arm shakes | Check `integrator="implicitfast"`, armature and damping in `scene.xml`. |
| Arm sags | Raise `kp`, or enable gravity compensation. |
| `IK failed at ...` | The point is outside what the arm can reach while pointing down. See known limitations. |
| `link6` not found | Check the `<body name=...>` entries in `xarm6.xml`. |
| Windows `find` / `head` errors | Use `dir /s /b` and `findstr` instead. |

## 12. Roadmap

1. **Obstacles:** add box geoms to the scene and build an occupancy grid from them, inflated by the size of the tool and the carried piece.
2. **Planner baseline:** A* over the occupancy grid, replacing `make_path`. This is the reference for judging the RL policy.
3. **RL environment:** a fast 2D grid environment (no physics) with randomized start, goal and obstacles each episode, trained with PPO (stable-baselines3). Start with an empty grid and add obstacles gradually.
4. **Evaluation:** measure success rate and path length against A* on layouts the policy has never seen.
5. **Bridge to MuJoCo:** run the trained policy's moves through `move_to_xy`, with the real gripper position fed back each step.
6. **Gripper model:** a suction tool with a site at the tip, and attach/release logic.
7. **Computer vision:** detect the wooden piece from a simulated camera and convert pixels to table coordinates.
8. **Pick and place** around the planned path.
9. **Real arm.**

## 13. Moving to the real arm

The sim and the real setup should share one coordinate frame, chosen as the **robot base frame** in meters. Nothing needs scaling because MuJoCo already works in meters.

What to measure on the real setup (relative to the base):

1. The board corner position (x, y).
2. The board height (z).
3. The board rotation relative to the base axes (aligning it square with the arm is easiest).
4. The cell size.

A more accurate method is to jog the real arm to touch the board corners and read the end-effector pose reported by the controller (the xArm reports millimeters, so divide by 1000).

Other points:

- Set the tool center point (TCP) offset on the real controller so commanded positions mean the cup tip, matching `TOOL_OFFSET`.
- The xArm SDK accepts Cartesian targets and solves IK on the controller, so the real arm needs only the target cell converted to (x, y, z) and an orientation.
- The arm geometry transfers from the URDF. The simulated dynamics (`kp`, `kv`, damping) do not, since the real arm has its own controller.
- A camera adds a pixel-to-board calibration step (for example, markers at known board corners and an OpenCV homography).
- For first runs: slow speeds, e-stop within reach, controller workspace limits set, and one cell at a time.
